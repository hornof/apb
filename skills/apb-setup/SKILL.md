---
name: apb-setup
description: Interactive setup for a new apb project — repo, board, collaborators, permissions, Claude's GitHub account, optional @claude review bot. Use once per project. CI and hosting are NOT set up here; they come after the TDD (apb-tdd step 5).
---
This skill belongs in the orchestrator (the main Claude Code session, opened in the project directory) — it needs git and gh. Walk the user through these in order, doing everything you can yourself (create the repo with `gh repo create` when gh is authenticated) and prompting them only for truly manual steps, one at a time:

0. **Right folder, before anything else.** The project folder is the folder the human named for this project; if they haven't named one, ask. Compare it with this session's working folder, both resolved to real paths (`pwd -P` for this session's; `cd <project folder> && pwd -P` for the project's), so a link such as `/tmp` for `/private/tmp` doesn't count as a difference. If they differ, stop and tell the human in one line:
   open a new Code session with the folder set to `<project folder>` and run `/apb-setup` there.
   Do nothing else first: no repo, no board, no branch, no commit, no file written. Why: the project's `.claude/settings.json` (the deny list) and `.claude/settings.local.json` (Claude's GitHub account and git author, step 5) apply only to a session opened in that folder. From another folder, commits show the human as their author and the deny list doesn't cover this session, so step 7's check can't work. If the folder doesn't exist yet, make it, empty, before you stop, so the human can open the new session in it.
   Then the prerequisites: verify `git` and `gh` are installed and `gh auth status` shows a logged-in account with the `project` scope — fix these first (install, then `gh auth login`; if `gh auth status` lacks the `project` scope, run `gh auth refresh -h github.com -s project` — a one-time human step with a browser login; Claude cannot do it), because every later step that touches GitHub assumes Claude can act there without the human clicking through the website.
1. Repo: ask whether it should be public or private (never decide this yourself), then create it with `gh repo create`, then create the board (step 3) and publish a first version of the map artifact (step 1a) before the initial commit, so the board link and the map artifact link are filled in and no placeholder is ever committed. The map artifact link goes in both docs/MAP.md and CLAUDE.md. The only placeholders that stay are `<apb plugin folder>` and `<output.html>` in CLAUDE.md's map rule: they name a folder and a file on whichever computer runs the command. Push an initial commit straight to main with: templates/CLAUDE-template.md as CLAUDE.md; templates/README-template.md as README.md with the project name and one-sentence description filled in; templates/LOG-template.md as LOG.md; templates/LESSONS-template.md as LESSONS.md; templates/gitignore-template as .gitignore; templates/MAP-template.md as docs/MAP.md; templates/reviewer-notes-template.md as docs/reviewer-notes.md; templates/HISTORY-template.md as docs/HISTORY.md, keeping the intro and the Setup entry and leaving out the examples and later stages. Fill in every other placeholder (text like `<project>`) before committing; none may remain in any committed file. Once `docs/MAP.md` exists, the plugin's hooks start writing `.apb/events.jsonl` (see the playbook's "The events file"); the `.gitignore` keeps `.apb/` out of git.
   - This is the only direct push to main the project ever gets: there is no branch to open a PR from yet. `.claude/settings.json` is not in it on purpose. Its deny list forbids pushing to main, and Claude Code applies it as soon as the file exists in the folder, so writing it first would block this push.
   - Right after the push, make a `setup` branch from main (`git switch -c setup`). Every later setup change, such as the PRD input links (step 1b), the collaborator guide (step 2), the deny list (step 4c) and the account rows (step 5f), goes on the `setup` branch, and step 7 lands it through a PR. Changes for the `setup` branch are made but not committed until step 5e shows the account (or the human said no to it in step 5); then commit them all at once, so every `setup` commit is by the account. Before step 5c, git still signs commits as the human. The human never runs a git command during setup.
1a. Map artifact: the map lives in two places, `docs/MAP.md` and the map artifact, a Claude artifact built from it. Claude edits only `docs/MAP.md`.
   - Before the initial commit (step 1), publish a first version of the map artifact, for example a page that says "Map coming", to get its link. Put the link in `docs/MAP.md` (the intro and the map artifact's row) and in CLAUDE.md's map rule.
   - After the initial commit is pushed, build the map artifact from `docs/MAP.md` and publish it to that same link: `python3 <apb plugin folder>/scripts/map-artifact.py <output.html> <map artifact link>`. The apb plugin folder is two folders above this skill's base directory.
   - From then on, build and publish it again after every change to `docs/MAP.md`, and again from main after each merge. Never edit the artifact by hand.
   - The progress page gets its own artifact the same way: before the initial commit, publish a first version to get its link, and put the link in the progress page's row in `docs/MAP.md`. After the initial commit is pushed, build it with `python3 <apb plugin folder>/scripts/progress-page.py <output.html>` and publish it to that link.
1b. PRD input issue: open an issue called "PRD input" that lists these questions for the human to answer:
   - What should it do?
   - Who is it for?
   - What similar products do you like? Include links.
   - What's a must-have, and what's a nice-to-have?
   - Public or private?
   - Where will people use it: a website, a phone app, a command-line tool, something else? If it's online, what address?
   - Anything you're not sure is technically possible, or that depends on another site or service cooperating?
   - Any deadline?

   Link the issue from docs/MAP.md and docs/HISTORY.md. Add the issue to the board (step 3) in In progress. Move the card to the top of In progress (see apb-build step 1). When the PRD stage starts, close the issue; the board moves it to Done.
2. Collaborators: ask whether anyone else will work on the project.
   - If not, remove the collaborator-guide row from README.md and go on to step 3.
   - If so, ask for each teammate's GitHub username and invite them. Then copy docs/collaborator-guide.md into the project's docs/ folder, adapted for this project.
3. Projects board: create with columns Todo / In progress / In review / Done; link the repo. Then put the board's URL into README.md's last line.
   - A project has one board, never more.
   - The board's "Item closed" automation moves a closed issue's card to Done. It isn't always on by default, and GitHub's API can't turn it on; only the board's Workflows page in a browser can. Claude switches it on itself in step 5g, signed in as Claude's GitHub account, which doesn't exist yet here. A card moves to Done only when its issue closes; nobody moves a card to Done by hand.
   - From setup on, the board holds one issue per early stage: the PRD input issue (step 1b), then the PRD issue (apb-prd) and the TDD issue (apb-tdd). After the TDD, apb-board adds the build issues to the same board. So the board always shows where the project stands.
   - Each stage issue moves through the columns like any other issue. The PRD and TDD issues close when their gates' PRs merge. The PRD input issue is closed when the PRD stage starts.
4. Permissions. The goal is zero mid-session prompts. Five parts:
   a. **Auto mode lives in the human's own settings, never in the repo.** Read `~/.claude/settings.json`. If `permissions.defaultMode` isn't `"auto"`, show the human that one line and offer to add it (it's their file, so ask first). Repo files can't turn auto on, and a `defaultMode` in a repo file overrides the user's `auto`, which brings back a permission prompt for every command. Never write `defaultMode` into any repo file.
   b. **In the desktop app, the mode picker remembers a mode per folder and outranks the settings.** Tell the human to pick **Auto** in the picker for this folder once.
   c. **Shared allow/deny list, checked in.** Copy `templates/claude-settings-template.json` to `.claude/settings.json`; commit it on the `setup` branch with the other held changes after step 5e (step 1), so every collaborator and every worktree gets the same rules. It's the fallback when auto mode is unavailable; the deny list (no merge, no force push, no push to main) applies in every mode. `.claude/settings.local.json` stays git-ignored for personal additions, with no `defaultMode` and no one-off literal commands. The deny list applies to this session as soon as the file exists, so from here on a direct push to main is refused; that is why step 1 pushes the initial commit first.
   d. Check: in the desktop app, read this session's permission mode (`get_session` with "self") and confirm it says `auto`. Otherwise ask the human what the mode picker shows.
   e. **Protect `main` on GitHub** (ask first; it's a repo setting): require a pull request before merging. Deny-list patterns can miss a spelling such as `git push -u origin HEAD:main`; branch protection can't be missed. Then auto mode can't push to main by accident.
5. **Claude's GitHub account.** Give Claude Code its own GitHub account, so GitHub shows which PRs, comments, commits and board moves are Claude's and which are the human's. Recommend it; if the human says no, Claude keeps using the human's login and the signatures alone tell them apart, and commits the `setup` branch changes held since step 1 right away. If the human says no, still do step 5g, with Chrome signed in as the human, who owns the board. It comes after the repo and the board, because once it is set, `gh repo create` would make a repo under Claude's account.
   - One account for all of Claude Code: the orchestrator, the builders and the reviewers share one `gh` login on the laptop, and the role signature (`— Claude (orchestrator)`) tells them apart. The advisor, in Cowork, posts through its own GitHub connection as the human, with its signature. The human reviews and merges as themselves.
   - If the account already exists from an earlier project, skip step a. Ask the human for that project's folder: in step c, pass its `.claude/settings.local.json` to `claude-account.py` in place of a token file, and the script copies the token from there.
   a. **The human's steps**, one at a time, in a private browser window so their own login isn't in the way:
      - Create the account at github.com/signup, for example `<human's login>-claude`. GitHub allows each person one free machine account. It needs an email address the human's own account doesn't use; an alias the human can read is enough.
      - Turn on two-factor login for it (Settings → Password and authentication). GitHub requires it.
      - Signed in as the new account, make a classic token at github.com/settings/tokens/new with the scopes `repo`, `project`, `read:org` and `workflow`, and nothing else. The expiry is the human's choice. It must be classic: fine-grained tokens can't reach Projects boards owned by a user account, and the board is user-owned. `read:org` is needed by `gh project` commands that take `--owner`: `gh` asks GitHub whether the owner is a user or an organization, and without `read:org` that question fails with "unknown owner type". `workflow` is needed when git uses `gh` to sign in for pushes: GitHub refuses a push that changes a file in `.github/workflows/`, such as the CI workflow (apb-tdd step 5), from a token without it.
      - Save the token in a text file that holds nothing else, for example `~/Downloads/claude-token.txt`, and tell Claude the path. The token goes in the file, never in the chat: everything in the chat is saved to disk and may be copied elsewhere.
   b. **Give the account access**, running as the human: prefix each command with `env -u GH_TOKEN`, so `gh` uses the human's own stored login even when the token is already set.
      - Add the account to every repo the project uses, with write access: `env -u GH_TOKEN gh api -X PUT repos/<owner>/<repo>/collaborators/<account> -f permission=push`.
      - The account has write access, not admin. So from now on, repo settings that need admin rights, such as collaborators, branch protection, Pages and secrets, run as the human: prefix the command with `env -u GH_TOKEN`.
      - Add it to the board as Admin, with GitHub's GraphQL mutation `updateProjectV2Collaborators`: `env -u GH_TOKEN gh api graphql -f query='mutation($p: ID!, $u: ID!) { updateProjectV2Collaborators(input: {projectId: $p, collaborators: [{userId: $u, role: ADMIN}]}) { collaborators { totalCount } } }' -f p=<board id> -f u=<account's node id>`. `gh api users/<account> --jq .node_id` gives the node id. It is Admin on the board only; on the repo it stays at write. The board's Workflows page, where step 5g switches on "Item closed", opens only for a board admin.
   c. **Store the token.** From the project's root, run `python3 <apb plugin folder>/scripts/claude-account.py <token file>`. It never shows the token. It checks that `.claude/settings.local.json` is git-ignored, asks GitHub who the token signs in as and which scopes it has, and refuses a token without the four scopes. It also refuses the human's own token, made by mistake while signed in as the human: it compares the token's login with the human's own `gh` login. Then it writes an `env` block into `.claude/settings.local.json`: `GH_TOKEN`, plus `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` set to the account's login and its `<id>+<login>@users.noreply.github.com` address. Last, it deletes the token file.
      - Why this works: `gh help environment` says `GH_TOKEN` "takes precedence over previously stored credentials". Claude Code sets the `env` block in its own shell only, so Claude's `gh` acts as the account while the human's terminal stays logged in as the human. The `GIT_*` variables override git's own name and email in every worktree, so commits show the account without changing any git config.
      - Never put the token in `.claude/settings.json`, which is committed, or in any other repo file.
   d. **Accept the repo invitations as the account**: `gh api user/repository_invitations` lists them, and `gh api -X PATCH user/repository_invitations/<id>` accepts one. With the token set, these run as the account, so the human doesn't have to.
   e. **Check.** `gh auth status` shows the account, marked `(GH_TOKEN)`, as the active account, and `env -u GH_TOKEN gh auth status` shows the human as active. `git var GIT_AUTHOR_IDENT` shows the account's noreply address. If the first still shows the human, ask the human to start a new Claude Code session in this folder. Once it shows the account, commit the `setup` branch changes held since step 1 in one commit. Then post one comment on the PRD input issue: GitHub shows the account as its author. Keep the signature on every PR and comment anyway, since it names the role.
   f. Add two rows to `docs/MAP.md`: the account, under outside services, and the token in `.claude/settings.local.json`, under the developer's computer.
   g. **Switch on the board's "Item closed" workflow**, so a closed issue moves its card to Done. GitHub's API can't do it, so Claude does it in Chrome (Claude in Chrome), signed in as Claude's GitHub account, which is now Admin on the board (step 5b), or as the human, who owns the board.
      - First, check which GitHub account Chrome is signed in as: open github.com and read the login on the avatar menu. Either Claude's GitHub account or the human will do. Only if it's neither, ask the human to sign in to github.com in Chrome as one of them; that sign-in is theirs, since Claude never types a password. If the human said no to the account (step 5), the login must be the human's, who owns the board.
      - Then, on the board: Workflows → Item closed → Edit → set Status to Done → Save and turn on. Reload the Workflows page and look again: "Item closed" must show as on, with Status set to Done.
      - Only if this fails (Chrome can't be reached, or the page won't save), hand the human one clear step: the board's link and those same clicks, in a browser signed in as the human or the account. Then look again to confirm it is on.
   - Upkeep: when the token expires, the human makes a new one with the same scopes, and Claude runs `claude-account.py` in every project folder that uses the account. Each new repo gets steps b and d.
6. OPTIONAL @claude review bot on the user's subscription: run `/install-github-app` and choose the subscription-token path ([docs](https://code.claude.com/docs/en/github-actions)). Skip unless asked.
7. **Land the setup branch.** Push the `setup` branch (`git push -u origin setup`) and open a PR from it with `gh pr create`, titled "Setup", listing what it adds. Claude never merges: the human merges it on GitHub, with the merge button, not a git command. Then switch to main and pull it (`git switch main`, `git pull`), so `.claude/settings.json` with the deny list is on main and in the folder. Check the deny list: run `git push origin main` yourself, in this session, as one command. Claude Code must refuse it. Step 0 put this session in the project folder, so its deny list is the project's; never start another Claude Code to run the check. After the pull, local main matches GitHub's, so if the push runs, it only prints "Everything up-to-date": the deny list isn't working. Tell the human, and fix `.claude/settings.json` in a new PR before going on.

Do NOT set up CI or hosting here: there is no stack yet, so a CI workflow has nothing to run and a hosting connection has nothing to build. Both happen right after the TDD is approved (apb-tdd, step 5).

Never store tokens in the repo; confirm each step worked before the next.
