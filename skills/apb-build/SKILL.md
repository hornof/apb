---
name: apb-build
description: Build the next unblocked issues from the project board, tests-first, one flat PR each. Use during the build loop, after gates 1 and 2.
---
1. Take the top unblocked issue from the board's Todo column, and start its build with `python3 <apb plugin folder>/scripts/board-move.py start-build N`, from the project's root. It moves the card to the top of In progress; then launch the builder (step 2), as an agent or a separate build session. There is no other way to start a build, and builders never move cards. An issue is unblocked only when every issue it needs is merged.
   - Every card you move goes to the top of its new column, so the human sees the latest movement first. `board-move.py` does that (`updateProjectV2ItemPosition` with no `afterId`). For any other move, `gh project item-edit` sets the column but not the place in it, so then run `updateProjectV2ItemPosition` with the board's id and the card's item id, and no `afterId`. Todo is the order the cards will be built in, with the next card on top.
   - The end-of-turn check (`scripts/consistency-check.py`, run by the Stop hook) sends back a turn that leaves a card in Todo while its build runs, and the other board and GitHub mismatches the playbook lists in "Rules a script can check".
2. Launch the plugin's `builder` agent on it (it opens one flat draft PR closing the issue as soon as it starts, then writes tests from the acceptance criteria first, then code until green, then marks the PR ready for review). The brief gives the builder its own scratch folder, named after its issue (for example `scratchpad/issue-14/`), and says to keep every file it writes outside the repo in that folder. Agents running at the same time otherwise overwrite each other's files, such as a PR description.
   - The brief gives the task only. It never says how to format or post the work: that is in `agents/builder.md`. The plugin's hook refuses a brief that does: words like "as a single comment", "post as" or "use one thread", or "format" next to review, comment, report or PR. If it refuses yours, take those words out and launch the agent again.
3. Build independent issues in parallel. If other unblocked issues can be built at the same time (its "Can be built at the same time as" line names them), start a builder on each one now.
   - Give each builder its own git worktree, made from freshly fetched main, and keep the builder in it. A builder's shell starts in the session's main checkout, so a command that names no folder runs there and tests main's code, not the PR's. Do one of these:
     - Launch the builder with the Agent tool's worktree isolation (`isolation: "worktree"`), so its shell starts in the worktree. That worktree may start from the session checkout's current commit rather than fresh main, so the builder still branches off freshly fetched `origin/main` itself, as `agents/builder.md` says.
     - When you make the worktree yourself with `git worktree add`, the brief names it and says every command names the worktree with a folder option or an absolute path, such as `git -C <worktree>` or `python3 -m unittest discover -s <worktree>/scripts -t <worktree>/scripts`, or runs a script that changes folder itself (the command rule in `agents/builder.md`), so no command runs in the main checkout.
   - Before you trust a builder's test results, check that they ran in its worktree: the command names the worktree's path, or its output does, or the builder was launched with worktree isolation and the command names no other folder. If they ran in the main checkout, have the builder run them again in the worktree.
   - Don't start an issue early, even if its dependency's PR is open. Wait for the merge.
4. Never wait without the watcher (see the playbook's "While Claude waits"). The plugin's hook keeps the watcher running for your session, on the project's repo and the coordination issue in `CLAUDE.md`, and wakes you when it finds something. When that issue is in another repo, the hook runs a second watcher on that repo. While a builder or reviewer runs, also keep your own watcher running in the background in your own shell:
   `python3 <apb plugin folder>/scripts/apb-watch.py --state <your scratch folder>/watch.json --check-in 5 --issue <the card's issue>`
   - The apb plugin folder is two folders above this skill's base directory.
   - When it exits, act on what it printed, then start it again. If something is stuck, stop it, restart the step, then tell the human.
   - Check before stating: every status, time or "still waiting" comes from a check in the same turn (`gh pr view`, `date`). Each status line says when the step should finish.
   - Each time you say who holds the ball, run `python3 <apb plugin folder>/scripts/human-turn.py` from the project's root and clear every stale flag it reports with the `--remove-assignee` command it prints (see the playbook's "Assign the card to the human while it waits on them").
   - Before you ask a decision again, or say it is still open, read its thread in the same turn: for a Decision on a PR, `python3 <apb plugin folder>/scripts/decision-check.py N` (it says whether the thread is resolved or answered); for one asked on the card, `gh issue view N --comments`. A watcher line about a merge says nothing about a reply on the card.
5. Once per project, on the first build PR with real logic, tell its builder to run the deliberate-bug check (see the playbook's "Testing and models"). Builders don't run it otherwise.
6. For an issue marked "Early look", the builder posts the preview link on the issue as soon as a first version is up. Don't stop the build to wait for the human. If they comment, the builder takes it into account.
7. Before the builder marks the PR ready for review, check that it finishes the whole card. A PR closes exactly the cards it finishes, with "Closes #N". If it will do only part of a card, split that part into its own card first, and have the PR close the new card.
8. The card stays In progress while the PR is a draft: never move it when the draft opens. When the builder marks the PR ready for review, move the card to the top of In review: the plugin's hook does it the moment `gh pr ready` succeeds, for each card the PR closes, and says so. If the hook says it couldn't, or the PR was marked ready another way, run `python3 <apb plugin folder>/scripts/board-move.py pr-ready M` (it refuses a draft). Then run `apb-review`. It runs one review round, and the builder fixes the Fix items before the human sees the PR.
9. If an agent's report says it departed from its instructions, stop and put it right before the human sees anything.
   - The plugin's hook catches a report with "departed from" or "as you asked, instead of", and sends back every hand-off to the human, up to 3 times a turn, until it is resolved. Once it's put right, run `python3 <apb plugin folder>/hooks/apb-brief.py resolve "<what you did>"` from the project's root.
10. Hand the PR over as `apb-review` says. When there are Decisions, also point to the PR's "What to look at" section. The human may have watched along the way, so don't present the PR as new. If the issue had an early look, say what changed since then.
   - When a Decision thread is resolved, reply in it `Resolved = <letter>: <what you'll do now>`, and do it.
   - In the same turn, assign the card and the PR to the human: `gh issue edit N --add-assignee <login>` and `gh pr edit M --add-assignee <login>`. Do the same whenever a card waits on the human for a question on the card.
11. After the merge, the card moves to Done on its own: "Closes #N" closes the issue, and the board's "Item closed" automation moves the card. Nobody moves a card to Done by hand. If the card hasn't moved, find out why the issue didn't close.
   - The automation puts the card at the bottom of Done. Once it's there, move it to the top of Done, as in step 1.
   - In the turn you notice the merge, unassign the human from the card and the PR: `gh issue edit N --remove-assignee <login>` and `gh pr edit M --remove-assignee <login>`. Do the same when the human answers a question on the card.
   - Post the card's times on the closed issue, from the project's root: `python3 <apb plugin folder>/scripts/card-times.py N --post --guessed "<the times you guessed>"`. It works out the build, review and human minutes, and the human's messages beyond "go", a decision letter, "resolved" or "merged", from the events file and GitHub. Never write these times by hand (see the playbook's "Say when each step should finish").
