# Repo rules (apb)
## Who does what
- **Orchestrator** — the main Claude Code session, the one the human talks to. It drafts the PRD and TDD, keeps the board, and runs the build loop: take the top unblocked issue, and any others that can be built at the same time → start a builder on each → when the PR is open, spawn the reviewer → hand the PR to the human → after the merge, check the live product. It does not write feature code itself and never merges. It starts each builder and reviewer with a brief, can message one while it runs, gets its final report, and can read its full log on the laptop (playbook, "How the orchestrator and the agents talk").
- **Builder** — a subagent the orchestrator spawns (`agents/builder.md` in the apb plugin). Writes the tests, then the code, opens one flat PR. Starts with no memory of the chat.
- **Reviewer** — a subagent the orchestrator spawns in a fresh context (`agents/reviewer.md`). Reviews the PR and the live product; writes no code.
- **Advisor** — optional; a Claude session outside the repo (Cowork) with broad access: thinking through the idea, research, independent reads. Never writes to the repo; its input is a comment on the relevant issue.
- **Human** — approves the three gates and merges.
## Rules
- Tests before code; one feature per flat PR off freshly-fetched main; never stack branches or push to a merged branch.
- Only humans merge. The reviewer is a separate session; it writes no code.
- Every PR gets one review round from the reviewer before the human sees it, whether it holds code or only docs. The reviewer reads `docs/reviewer-notes.md` first. The Fix items are fixed and checked before the human looks. Fix items go in one post and Notes in one post or a section of the Fix post; only Decisions get threads, one thread each. Each Decision has the question in one sentence, lettered options, `Recommended: <letter>` and `Resolve with no reply = <letter>`. A builder implements a Decision only once its thread is resolved or the human's last reply names an option letter. With no Decisions, the hand-off is one line: "1 thing for you to do right now: merge PR #N.", with the PR as one link, plus `Preview: <link>` if the PR changes how the product looks. The orchestrator adds each of the human's overrides and new rules to `docs/reviewer-notes.md`.
- After every merge, check the live product (the site, the published package, the released app), not just CI.
- The Projects board is the single progress tracker; PRs reference their issue.
- When something goes wrong, add a rule here the same day.
- Approved PRD/TDD wording is immutable except by the human's explicit choice.
- Permissions: sessions run in auto mode (set in each human's `~/.claude/settings.json`; never put `defaultMode` in a repo file). At session start the orchestrator confirms the mode is auto (desktop: `get_session` "self"); if not, it tells the human in one line before anything else. One plain command per shell call: no `$(…)`, loops or `curl | grep` chains. Use WebFetch for web pages and a script file for multi-step logic. Every instruction to a builder, reviewer or research Claude repeats this command rule, since their permission prompts reach the human too. If a permission prompt appears mid-session, add the missing rule to `.claude/settings.json` the same day. Never type commands into the desktop app's Terminal panel: it asks the human every time, even in auto mode. To run something in another folder, use `git -C <folder>` or a script that changes folder itself.
- While an agent runs or a PR waits on the human or GitHub, apb's watcher runs (playbook, "While Claude waits"). The plugin's hook starts it and also watches the coordination issue named here, with a second watcher when that issue is in another repo. Every status, time or "still waiting" comes from a check in the same turn.
- coordination: (none yet; write `#N`, or `owner/name#N` for an issue in another repo, once the orchestrator and the advisor have an issue to talk on)
- Every brief to a builder, reviewer or research Claude gives it its own scratch folder, named after its issue or PR (for example `scratchpad/issue-14/`), and says to keep every file it writes outside the repo there. Agents running at the same time otherwise overwrite each other's files.
- `LOG.md` is append-only. A question for a human or the advisor goes on the card's issue — nothing important lives only in chat.
- Working with the human: follow the sections "How the human reviews", "Helping the human keep track" and "What the orchestrator does itself" in the playbook (`docs/playbook.md` in the apb plugin). In short: one question at a time, in plain chat; a merge or a clear yes is approval, but praise that comes with open questions is not; at the PRD and TDD gates, get the yes before the merge, so the post-approval updates go into the same PR; show everything visual; one link per thing.
- The human and Claude are never both idle at once. When the orchestrator stops working (the turn in which the last running thing finishes), its message starts with one of four lines: `Nothing for you to do right now. Waiting on <what>, ETA <time>.`, with a clock time (only while something is running or waiting on GitHub), `1 thing for you to do right now: <the thing>.`, `N things for you to do right now:` followed by a numbered list, or, once, when nothing is open on any board or repo you watch, `All clear: <boards> empty, no open PRs, as of <time>.` with nothing under it. The count is the real count. Then one line per card in In progress and In review, with when it should finish. Say the line once, when the orchestrator stops working. Say it again only when the thing changes: a new PR is ready, a decision appears, or the wait ends. In between, an answer to a question is just the answer, with no first line. Alert the human, with a sound, once with each new "1 thing", "N things" or "All clear"; never with "Nothing". A question gets an answer, not an action. Run commands yourself; only approvals, merges, sign-ins and app restarts are the human's. Never say it's late or suggest stopping.
- When you add a new piece (a Claude artifact, a folder, a scheduled task, an outside account), add it to `docs/MAP.md` at the same time. After each stage, add an entry to `docs/HISTORY.md`: the stage's decisions, surprises and changes of mind.
- Check every row of `docs/MAP.md` against GitHub, the Claude artifacts, the developer's computer and the outside services after every merge, whenever a PR opens, at the end of each stage, and whenever the human asks where things stand. Fix any row that is wrong. The map never copies a status, such as the current stage or whether a PR is open. Link the board or GitHub's live list instead.
- At those same four moments, check the board: every issue is in the right column, and there is an issue for the current stage. Fix what is wrong.
- The map lives in two places: `docs/MAP.md` and the map artifact, built from it. Edit only `docs/MAP.md`. After every change to it, and again from main after each merge, run `python3 <apb plugin folder>/scripts/map-artifact.py <output.html> <map artifact link>`, then publish `<output.html>` to that same link. Never edit the map artifact by hand.
- The progress page shows the status the map leaves out. Each time you wake up (a watcher exits, an agent reports back), each time you say who holds the ball, and whenever the human asks where things stand, run `python3 <apb plugin folder>/scripts/progress-page.py <output.html>`, then publish `<output.html>` to the progress page link in `docs/MAP.md`. Never edit it by hand.
- Before showing the human a markdown doc, check how GitHub displays it: `gh api markdown -F mode=gfm -F text=@<file>`.
- In a public repo, never name anyone who isn't on the repo.
- Claude Code works on GitHub as its own GitHub account when the project has one (apb-setup step 5), and as the human otherwise. Its token lives only in `.claude/settings.local.json`, never in a committed file. The orchestrator, builders and reviewers share that one account, so end every PR description and comment Claude writes with its role, for example `— Claude (orchestrator)`.
- Problems with the apb process itself go on hornof/apb as one issue per problem, labeled `from-` followed by this repo's name.
